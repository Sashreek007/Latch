Latch · MVP Build Plan

The execution companion to the design doc: sixteen chunks, M0–M15, ~99 hours, five weeks. Two pillars, both load-bearing — a durable execution engine for AI agent workflows, and a cloud-native AWS deployment that exists from week one and stays deployed. Thin every axis, drop none: every resume filter in the JD map keeps a real, demonstrable artifact. Node + TypeScript + Postgres at the correctness core, the core loop framework-free; models behind a port (OpenAI and Bedrock); AWS everywhere the correctness path isn't. This is a living document: statuses on the board below flip as chunks land.

0. What the MVP is — and isn't

A re-slicing of the full plan (C0–C20) for shipping fast: thin every axis instead of dropping axes. Every keyword in the JD map keeps a working artifact; what's deferred is depth — the second demo workflow, Redis, stall heuristics, the 50-case suite — never coverage. The architecture is unchanged from the design doc; every chunk below cites the decisions and deep dives it implements, so nothing here is designed twice.

Three of the sixteen chunks — M2 (deploy the skeleton), M12 (the cloud-native surface) and M13 (the production edge) — have no ancestor in C0–C20. The design doc's chunk list predates this plan's second pillar, and its stretch item S4 (Kubernetes manifests) is not the same thing. They are new work, priced as new work. M14 is also larger than its C14 ancestor: it promotes two COULD-tier items — a live-updating dashboard and a cost page — into the MVP.

Throughout: §N and DN always name a section or decision in the design doc. This document's own parts are 0, 1, 2, the chunks M0–M15, and R1–R3.

Concept · the governing principle — managed services everywhere except the correctness path

The engine core does not change because it moved to AWS. One Postgres holding queue, state, events, intents and effects in a single transaction, plus long-lived leased workers — that is roughly 15% of the system, and it is the 15% carrying invariants I1–I4. Every argument in the design doc rests on those two sentences, so nothing managed is allowed inside them.

Everything around that core is AWS-native and bought, not built: models (Bedrock), scaling (ECS target tracking), metrics and alarms (CloudWatch), artifacts (S3), secrets (Secrets Manager), provisioning (CDK), deploys (GitHub Actions over OIDC). The two pillars are not in tension — the first says where correctness lives, the second says everything else is someone else's problem. Pillar 2's chunks are not additive and are not the first thing dropped; the drop order in R2 says so explicitly.

1. Build rules & the arc

The three rules (unchanged from the design doc) — and a fourth this plan adds

1 · Walking skeleton first — M1 runs SDK→API→worker→Postgres end to end before anything is durable or agentic. 2 · The demo is the dev workload — the ticket workflow exists from M1 and thickens every chunk; integration is continuous, never an event. 3 · No capability without its falsifier — each engine chunk ships with its harness invariant, and a gate is trusted only after it has been seen red once (break the mechanism deliberately, watch the seed fail, revert).

4 · Both environments stay green. From M2 onward every chunk ships to both — the local Compose stack and the AWS deployment, the latter by CI on merge. A chunk is not done because it works on the laptop, and the per-chunk sections below do not repeat this; it applies to all of them. The single deliberate exception is the harness, for the reason given in part 2.

2. The cloud position — what runs where, and what was rejected

Pillar 2 is a claim about when, not just what: the system is deployed at M2, while it is still two tables and one endpoint, and stays deployed for the rest of the build. M2 makes the case for that ordering where it lands. This part settles the two questions that come before it — why there are two environments at all, and which AWS services were deliberately not used.

Concept · the two-environment rule

Local (Docker Compose) is the development and verification environment. AWS is the production environment. Both are first-class; from M2 onward, both stay green.

The split is not squeamishness about the cloud — it is where each environment is genuinely better. The inner dev loop runs in seconds against a container on localhost. The invariant harness sweeps thousands of seeded crash schedules against local Postgres in minutes; the same sweep against RDS would be slower, cost money per seed, and prove nothing extra — it is the same engine code issuing the same SQL, and the algorithm does not know which host its Postgres runs on.

So the harness (M4) is deliberately local-only, and the M12 gate re-checks the local sweep rather than moving it. The M14 stranger-clone test stays docker compose up: a stranger must be able to reproduce every published number without an AWS account. What the cloud environment proves is precisely what one machine cannot — cross-host lease takeover (M3), autoscaling against real queue depth (M12), IAM-scoped secret access, and that the thing deploys at all, repeatedly, from code.

Decision 23 Which AWS services — and which are deliberately rejected?
Rebuild AWS-native — Step Functions for orchestration, SQS for the queue, DynamoDB for the log, Lambda for workers. Maximum managed-service surface and the most keywords per hour of work. It also dismantles every load-bearing argument in the design doc, one service at a time (enumerated below).
Lift-and-shift onto EC2, or EKS — run the Compose stack on instances, or on a Kubernetes cluster, and change nothing. Cheapest to think about, but it proves only that Docker runs on Linux; there is no managed-service signal in it, and EKS adds ~$73/month for a control plane nobody in this project needs.
Managed services everywhere except the correctness path — ECS Fargate (compute), RDS Postgres with pgvector (the one stateful system, unchanged in role), Secrets Manager + IAM task roles (credentials), CloudWatch (metrics, alarms, the autoscaling signal), S3 (large artifacts by reference), Bedrock (a second model provider behind the existing port), CDK in TypeScript (provisioning), GitHub Actions over OIDC (deploys, no long-lived keys). CDK rather than Terraform for one reason worth stating: it is the same language as the engine, so cdk synth is a unit-testable artifact in the same test run rather than a second toolchain.
We buy everything except the invariants. The rejections below are the substance of this decision — each one names the specific decision or invariant it would have cost, and none of them is a matter of taste. The interview answer this earns is a sentence that survives follow-up questions: managed services everywhere except the correctness path, and those were deliberate rejections, not oversights. This decision extends the design doc; it supersedes nothing. Where it touches D17 (model routing), the extension is spelled out in M6.
RejectedWhy — the specific cost, not a preference
Step FunctionsIt is durable execution — checkpointed state machines, retries, human-approval callbacks. Adopting it means AWS already built the exact thing this project exists to demonstrate, and the thesis evaporates along with D1: there is nothing left to record-don't-replay. The résumé line degrades from "built a durable execution engine" to "configured one." It is also the interview question most worth having a real opinion about, and having an opinion requires having built the alternative.
SQS as the workflow queue
(adopted as the ingress buffer — M12)		As the workflow queue it reintroduces the exact dual-write problem D2 rejected: enqueue and state transition would span two systems, so I1 and I2 would rest on an outbox pattern instead of one transaction. The queue there is not a throughput choice — it is where the correctness argument physically lives.

The rejection is directional, and only one direction is unsafe. Upstream of that transaction SQS is adopted: M12 buffers arriving work on a queue and ingests it with one Postgres commit, so a redelivered message dedupes on the idempotency key while a lost publish could not have been recovered at all. It never holds workflow state and no worker reads from it.
DynamoDB as the event logUndermines the single-transactional-store argument the whole correctness story is built on (D2, D8): the log, its same-transaction projection, the queue row and the effects table would no longer commit together, and "the projection cannot drift from the log" becomes a hope.
Lambda workersA 15-minute execution cap and cold starts are incompatible with long-lived leases and 5-second heartbeats (D5, D13). A worker that can be frozen or evicted mid-step is a lease that lies, which is the one thing §5 is built to prevent.
EventBridge Scheduler for escalation timersPostgres due_at rows with an index are already correct, and they are already claimed by the same query as everything else (§8). A second scheduling system buys nothing and adds a delivery guarantee to reason about at the exact moment a human is waiting.
EKS~$73/month for a control plane, bought for a keyword. Local kind remains the free option if Kubernetes is ever wanted (stretch S4), and the kill demo already gets its cross-host form on Fargate at M3 — which was the only thing Kubernetes was going to add.
Decision 24 Live updates — polling, SSE, or WebSockets?
Keep polling — TanStack Query on a 2 s interval. Already works, zero new failure modes, and honestly fine for one viewer. But the trace steps rather than flows, which is a visibly worse GIF, and every idle viewer costs a query per interval per workflow.
WebSockets — full duplex, and the reflexive choice. But the dashboard has nothing to send upstream that REST doesn't already handle (approve/deny is a POST), so half the protocol is dead weight — bought at the cost of an upgrade handshake, a hand-rolled heartbeat and reconnect story, and sticky-session concerns behind the M13 load balancer.
Server-Sent Events over a Postgres LISTEN/NOTIFY fanout — one-directional, which is the actual shape of the data flow; plain HTTP; EventSource reconnects automatically by spec; and the trigger rides the transaction that already exists, so it can never announce something that didn't commit.
SSE, and the notification is advisory. NOTIFY is issued in the same transaction as the event append, so it can never announce something that didn't commit — but it is also fire-and-forget, so a disconnected listener simply misses it. That makes it a hint to re-read and never a source of truth, which is the same rule D4 already applies to Redis. The consequence is what makes it safe to adopt: revert to polling and nothing but the frame rate changes. No invariant, gate or published number depends on this layer — which also makes it the first thing to cut if the calendar slips. One deployment note: an ALB's default 60 s idle timeout kills an idle SSE stream, which is the classic way it "randomly" dies in production.
Decision 25 The production edge — what earns a standing monthly cost?
Keep the M2 minimum — a public IP, no ALB, single-AZ, rolling deploys with no rollback. Cheapest, and enough to prove the engine runs on managed infrastructure. But the demo has no shareable URL, no TLS, and the résumé cannot honestly say load balancing, HA or zero-downtime deploys.
A full production posture — CodeDeploy blue/green with canary traffic shifting, multi-region, tuned WAF rules, a status page. Genuinely impressive, and roughly 3–4× the hours. In a portfolio context it demonstrates very little the basic form doesn't, because there is no real traffic for any of it to survive.
Only what earns its standing cost — ALB + ACM + Route 53, and ECS rolling deploys with the deployment circuit breaker set to roll back. Single-AZ, and no WAF, deliberately.
The test is demonstration per dollar per hour, not keyword count. This decision reverses M2's "no load balancer" — deliberately, and only once the ALB has three jobs at once (TLS termination, a stable hostname, and a health-checked rollback target) rather than one. Automatic rollback earns its place outright: paired with a deploy shipped mid-workflow it turns NFR 6's claim into a recording, for two lines of CDK.

Multi-AZ and WAF were considered and declined. Multi-AZ roughly doubles the database line and drops it out of free-tier eligibility, to buy a claim — "highly available" — nothing else in this project makes. WAF bills a standing monthly fee for a rule set that, with no untrusted traffic, has nothing to block; it would demonstrate configuration rather than defence. Each is about an hour and one CDK change if ever wanted — and declining them on a stated cost basis is a better interview answer than having configured them without a reason. The remaining cost is in R2, not hidden.
Honesty box · what this deployment is and isn't

It is a production-shaped deployment, not a production deployment. From M13 it has a load balancer, TLS and a custom domain. It does not have Multi-AZ, a WAF, canary traffic shifting or multi-region failover — each declined on a stated cost basis (D25) rather than overlooked — and above all it has no real traffic. Every one of those is a cost decision with a price attached (R2), which makes each a sentence in an interview rather than a surprise in one.

What it does prove is not small: the system runs on infrastructure it never ran on locally, provisioned from code, deployed by CI with no human touching a console, holding secrets it never sees, under IAM roles that bound what it can reach — and it survives, mid-workflow, both a host being killed (M3) and its database failing over (M13), with the invariants still holding.

M0. Scaffold 4h · ⊂ C0 + the cloud scaffold

Delivers: pnpm workspaces (packages/* · apps/* · infra, covering engine · sdk · api · worker · harness · dashboard · demos · infra); Docker Compose with a single pgvector/pgvector:pg17 service (vector support from day one — no compose change at M10, and no RDS parameter change at M2 either); node-pg-migrate with migration 001; Biome; GitHub Actions running install → lint → test on every push; and an empty RESULTS.md at the repo root, which every later chunk appends to with a date and a commit hash (R3). No Redis, by design.

Plus the cloud scaffold, before any real code:

  • CDK app skeleton in infra — TypeScript, so the infrastructure compiles in the same pnpm build as the engine and cdk synth runs in the same CI job as the tests (D23). Empty stacks: network, data, services. They synthesize; they deploy nothing yet.
  • GitHub OIDC to AWS — an identity provider and a deploy role whose trust policy is scoped to this repository. CI assumes a role; there is no access key in a secret store, and there never will be. This is four lines of CDK and it is the difference between "has AWS on the résumé" and "has never leaked a credential."

Doing OIDC now rather than at M2 is deliberate: credentials are the thing everyone retrofits, and retrofitting them means a long-lived key existed in the meantime.

Gate M0

docker compose up → pnpm migrate → pnpm test green locally and in CI; and CI authenticates to AWS through OIDC and cdk synth succeeds. Two badges exist before any real code does.

→ RESULTS.md: create the file now, empty. It has to predate the first measurement, or the first measurement gets written from memory (R3).

As built — two deviations, both deliberate. (1) Each workspace is created in the chunk that gives it its first real file, rather than eight empty shells at M0: six of them would have been a manifest plus a placeholder source that exists only so the typechecker does not error on an empty package, which asserts nothing and contradicts the vertical-slice rule. The gate tests commands, not directories. (2) Relative imports across the repo end in .ts, not .js — Node 24 runs the TypeScript directly by stripping types and does not rewrite import paths, so the .js convention resolves to a file that does not exist. allowImportingTsExtensions permits it; rewriteRelativeImportExtensions converts the specifiers back for the SDK's published build at M15.

M1. Walking skeleton + event log 5h · C1 + C2 thin

Implements §4 (event log & state), D8 (events authoritative + same-txn projection), D10 (JSONB + zod).

  • workflows + workflow_events tables per the §4 DDL — PRIMARY KEY (workflow_id, seq) from the start.
  • zod schemas for every event type; fold(events) → state; projection updated in the same transaction as every append.
  • ticket-v0 in demos: two code phases (lookup → reply stub) — no model, no durability yet.
  • API: POST /workflows (one txn: row + workflow_started + ready), GET /workflows/:id. A naive in-process worker runs code steps to completion.

The ticket demo gains: it exists, end to end. Everything here still runs only under Compose — which is exactly why the next chunk moves it, while it is still small enough to move cheaply.

Gate M1

curl start → status completed; events visible in psql; a re-fold of the log equals the projected row (assert in a test — this is the seed of latch verify).

M2. Deploy the skeleton 7h · new — no C-chunk ancestor the deployment

Implements D23. No design-doc decision is superseded and none is re-opened: the engine core is untouched by this chunk — it is the same code, reading its connection string from somewhere else.

  • ECR + one image, two task definitions. The API and the worker are the same image with different entrypoints, so a deployed worker and a deployed API cannot drift apart in a way that only shows up at 3am.
  • ECS Fargate — an API service (desired count 1) and a worker service (desired count 2; M3's cross-host demo needs two hosts, and starting at two means the lease path is exercised from the first deploy).
  • RDS Postgres 17, db.t4g.micro, with the pgvector extension enabled at creation (M10 then needs no infrastructure change at all). In private subnets, not publicly reachable: the only ingress rule is the tasks' security group.
  • Secrets Manager + IAM task roles. The database URL and the OpenAI key are secrets injected by the task definition; the task role grants secretsmanager:GetSecretValue on those two ARNs and nothing else. Least privilege written as one statement per secret is not hard — it is just usually skipped.
  • Workers in private subnets, with outbound egress — for the model and tool calls that arrive at M6 and M9 — through a single NAT gateway. The alternative considered was VPC interface endpoints instead: five of them (ECR api + dkr, Secrets Manager, CloudWatch Logs, Bedrock) run about $36/month against the NAT's ~$33, so endpoints become the better answer only once Bedrock is the only provider. At ~$0.045/hour the NAT is the largest standing line in the stack, which is precisely why cdk destroy between work sessions is part of the routine rather than an afterthought (R2).
  • No load balancer — yet. ~$16/month standing buys nothing while the only client is one developer and there is no domain to point at it. The API task takes a public IP on a public subnet with its security group scoped to one address. An ALB arrives at M13, when TLS, a custom domain and a rollback target give it three jobs at once — see D25, which reverses this line deliberately rather than quietly.
  • CI deploys on merge — build → push to ECR → cdk deploy → ECS rolls both services. The deploy job runs after the test job, an ordering that becomes load-bearing at M4.
Concept · why deployment is chunk two and not chunk fifteen

Deploying now, while the system is two tables and one endpoint, means the cloud's constraints — VPC networking, IAM boundaries, secrets that cannot be a .env file, config that must arrive from outside the image, container health checks, a database that is not on localhost — shape the build. Every chunk after this one is written against a system that already has them.

Deployed at the end instead, those same constraints arrive as a retrofit across nine chunks of laptop assumptions, in the final week, under time pressure. That is the specific way portfolio projects die with a README that says "cloud deployment: future work." The trade is legible: seven hours now, when there is almost nothing to deploy, against a configuration-and-secrets rewrite later, when there is everything.

The ticket demo gains: it runs somewhere other than the laptop that wrote it.

Gate M2 ✦

The same walking skeleton that runs under Compose completes a workflow on Fargate against RDS, deployed by CI, with zero manual console clicks. Then the round trip that proves it is really code: cdk destroy the whole stack, re-run the deploy from CI, and start another workflow. Infrastructure that survives being deleted is infrastructure; anything else is a console session with good documentation.

M3. Queue, leases, fencing 6h · C3 the kill demos

Implements §5 wholesale: the three SQL statements are the entire mechanism. JD: async / concurrent / queueing design (the Xanadu hard requirement).

-- the whole chunk in three statements (§5)
CLAIM:     UPDATE … WHERE id = (SELECT … WHERE ready OR lease expired
           ORDER BY run_after LIMIT 1 FOR UPDATE SKIP LOCKED)
           SET lease_token = lease_token + 1, … RETURNING lease_token;
HEARTBEAT: UPDATE … SET lease_expires_at = now() + ttl
           WHERE id = $wf AND lease_token = $token;   -- 0 rows ⇒ abort step
APPEND:    INSERT INTO workflow_events … WHERE EXISTS
           (SELECT 1 FROM workflows WHERE id = $wf AND lease_token = $token);
  • Worker becomes a real binary: claim → one step → checkpoint → release (D5, lease-per-step). Heartbeat 5s / TTL 15s (D13). Takeover is claim-time (D12) — no reaper.
  • Every write the worker makes is fenced by token and backstopped by the (id, seq) primary key (D11).
  • The Fargate worker service already runs two tasks (M2), so the cross-host path is live the moment this lands.

The ticket demo gains: it survives kill -9 on one machine — and the loss of a whole machine.

Gate M3 ✦ — two kill demos, because they prove different things

Local: two worker processes; kill -9 one mid-run; the other finishes. Zombie test: SIGSTOP a worker past its TTL, let takeover happen, SIGCONT — every write it attempts matches zero rows.

Cloud: aws ecs stop-task on the Fargate task holding the lease; a task on a different host claims it and finishes the workflow. This is the demo the lease mechanism was actually designed for. A single machine's kill -9 cannot distinguish "the lease works" from "the OS tidied up after us" — same kernel, same page cache, same clock. Two hosts and a hard stop remove that ambiguity, and until M2 there was no second host to remove it with.

The cloud version is slower to watch — task placement takes seconds, not milliseconds. Record it anyway; it is the more convincing of the two recordings at M15.

→ RESULTS.md: takeover latency, median and p95, from worker death to another worker executing — measured separately for the local kill and the Fargate cross-host kill. NFR 5 targets under 20 s; publish the actual, and publish both numbers. The Fargate figure will be worse, and the gap is the honest part.

M4. Harness v1 6h · C4 + C6 thin the eval spine local only

Implements §9: seeded schedules, logical workers, invariant sweep. JD: evaluation pipelines — the single strongest signal in the map — plus benchmarking and regression suites.

  • Logical workers (async tasks in one process), pure-rand seeded PRNG, injected clock; named crash points at every §5/§6 boundary; lease-expiry and tool-failure injection.
  • Invariants as pure functions over the finished log: I2 (every start reaches terminal/suspended) and I3 (zero fenced-write violations, no overlapping lease intervals).
  • pnpm sweep --seeds 500; a failing seed dumps fixtures/seed-N.json and becomes a permanent regression test.
  • The pipeline order matters here. CI runs a 200-seed slice per push against the runner's Postgres service container, and the M2 deploy job depends on it: nothing reaches Fargate that failed an invariant. The eval suite is a deploy gate, not a report.

This chunk is deliberately local-only — the two-environment rule gives the reason the sweep's home is the Compose Postgres and stays there. The consequence is the part worth noticing: the strongest evidence this project produces is generated on a laptop, which is why anyone can regenerate it on theirs.

Gate M4

500 seeds green. Then the break-it-once rule: comment out the fencing predicate → a specific seed goes red → revert. A gate that has never been red is trusted on faith.

→ RESULTS.md: sweep wall-clock, seed count and fixture count. Start the bugs-caught log here and keep it for the rest of the build — one line per real bug the sweep surfaces, with its seed and the invariant that caught it. Also log the per-sweep denominators: workflows started, crashes injected, takeovers performed, retries triggered. Zero means very little without them.

M5. Intents + effects 5h · C5 I1

Implements §6: intent-before-effect, step-scoped idempotency keys (D14), engine-level effects table (D15), D3's effectively-once claim.

  • intent_recorded event written before any side effect, carrying key wf_id·step_seq — stable across retries, recorded durably so even the dangerous-window retry recovers it.
  • effects table with idempotency_key PRIMARY KEY — the dedupe is a unique constraint, not a convention. ToolExecutor port: the key is a required parameter.
  • The ticket demo's reply tool becomes genuinely effectful; retries consult the effects table.
  • Invariant I1: for every key, executions(log, key) === 1 — counted over every seeded run.

The ticket demo gains: its side effects are effectively-once, provably.

Gate M5 ✦

Seeded crash between execute and settle → the retry dedupes; I1 green across the sweep. Break-it-once: derive keys per-attempt instead of per-step → I1 red → revert.

→ RESULTS.md: the count of side-effecting operations executed across the sweep — the denominator that turns "zero duplicates" into "zero duplicates across N operations". Break-it-once produces the first entry in the bugs-caught log; write it down the day it happens.

M6. Agent step + envelope + tiers 10h · C7 + C9 + D17 + D23 I4 cross-provider

Implements §7: decision recording, reserve-before-spend, routing. JD: state management for agent workflows · intelligent multi-model routing · cost · token optimization.

  • ModelClient port with three drivers: OpenAI (structured decisions via the SDK's zod-based structured-output helper), AWS Bedrock (the same structured-decision contract, authenticated by the task role — no API key to store, no secret to rotate, and locally the developer's own AWS profile), and the seeded fake for the harness.
  • decision_recorded events now carry provider alongside model id, prompt hash, tokens, dollar cost and latency. A trace answers not just which model decided, but on whose infrastructure and at what price. Resume reads the fact — the model is never re-asked.
  • The tier price table gains Bedrock's per-token prices. Reserve-before-spend needs no change: it already reads worst-case cost from a table, and a table does not care whose prices are in it.
  • Envelope: reserve-before-spend (reserve worst-case cost in the claim txn; the call never happens if reservation would cross the ceiling; settle actuals at record time) + maxSteps. Invariant I4 checked at every log prefix.
  • Ticket triage becomes a real model decision on the small tier; the policy-judgment phase declares the large tier.
Concept · cross-provider routing — extending D17, not overturning it

D17's pick stands unchanged: static per-phase tiers declared by the definition author, and its rejection of a dynamic classifier (a model call to route a model call) still holds. What changes is what a tier names. A tier was a model; a tier is now a (provider, model) pair. small may be an OpenAI mini model and large a Bedrock-hosted flagship, or the reverse, or both on one provider — the definition declares the tier, configuration maps the tier to a provider.

That is what the JD map means by intelligent multi-model routing: the choice is made on measured cost and latency across providers, from numbers this engine already records per decision, rather than from one vendor's catalogue. And because the mapping is configuration, the comparison is a config change and a suite run — which is exactly the experiment M11 publishes.

Honesty box · what the Bedrock driver proves and what it doesn't

It proves the port is real — three drivers, one interface, one structured-decision contract — and that IAM-authenticated model access works with no key anywhere in the system. It does not prove Bedrock is cheaper or better. The cost delta is whatever the routing suite measures, and it gets published in whichever direction it lands; a number that came out the wrong way is still a number, and pretending otherwise would undermine every other number in R3.

The ticket demo gains: a model chooses its investigation path — on whichever provider is the right price for that phase — and cannot outspend its envelope.

Gate M6

Crash after decision_recorded → resume makes zero additional model calls (the fake counts). Seeded runaway halts at the ceiling; I4 holds at every prefix across the sweep. And the routing suite runs with a Bedrock tier, reporting the measured cost delta against the OpenAI-only baseline. The fake driver is untouched, so the seed sweep is byte-identical to M5's.

M7. Scoping, risk classes, critic 5h · C8 + C18 multi-agent

Implements D7 (structural scoping), D9 (risk → approval policy map), D18 (proposer/critic). JD: multi-agent orchestration · guardrails · policy enforcement · access control — the first of the JD map's four canonical pillars closes here.

M12. Cloud-native surface 11h · new — no C-chunk ancestor autoscaling

Implements the second half of D23. The S3 piece is not new scope: it is the honest implementation of the guardrail §4 already specifies — state size cap enforced at settle; large artifacts stored by reference. JD: cloud infrastructure · message queues · autoscaling · observability · cost.

  • SQS as the ingress buffer. Workflow starts arrive on an SQS queue; a small ingest consumer reads a batch and performs the same single Postgres transaction POST /workflows already performs, then deletes the message. No engine code changes, and no worker ever touches SQS — see the box below for why that direction is the whole point.
  • Worker autoscaling on queue depth. A publisher in the API task emits, every 20 seconds, SELECT count(*) FROM workflows WHERE status = 'ready' AND run_after <= now() as a CloudWatch custom metric; an ECS target-tracking policy scales the worker service on ready-workflows-per-task. This is architecturally honest rather than convenient: the queue is a countable table (D2), so backlog is a count(*), not an inference. Scaling on CPU would be a lie about what a worker does — a worker blocked on a model call is idle CPU and a full pipeline, and CPU-based scaling would shrink the fleet exactly when the backlog is worst.
  • CloudWatch metrics, one dashboard, one alarm. Workflows started / completed / dead-lettered, step latency, lease takeovers, model spend. The alarm is on dead-letter depth > 0 — D20's exhausted-retry path becomes an operational signal instead of a table nobody reads.
  • Cost per workflow as a published metric, computed from the dollar amounts already inside every decision_recorded event (M6). The number was always in the log; this chunk puts it on a wall next to the infrastructure cost, which is the pairing that makes it an engineering number rather than a receipt.
  • S3 for large artifacts. Payloads above the §4 size cap are written to S3 and the event carries a reference — bucket, key, sha256, byte count. The log stays small and foldable; the artifact stays retrievable; the cap stops being a wall and becomes a boundary. The harness keeps a fake object store, so seeds stay deterministic and offline.
Concept · why a broker upstream of the transaction is safe, and downstream is not

The dual-write problem D2 rejected is directional, and D23 rejects SQS only on one side of it.

Database → then → broker (rejected). Commit the workflow row, crash before publishing, and the workflow exists with nothing that will ever claim it. Lost workflow, I2 violated, and no ordering of the two writes fixes it — reversing them produces a message for a workflow that does not exist.

Broker → then → database (adopted here). Consume the message, commit one transaction, delete the message. Crash before the delete and SQS simply redelivers into an insert that is ON CONFLICT DO NOTHING on the idempotency key. Redelivery is recoverable because the effects layer (M5) already exists; a lost publish is not recoverable at all.

So SQS sits upstream of the transaction that I1 and I2 are defined over. It never holds workflow state, the engine cannot tell it is there, and the correctness argument is untouched — which is precisely why D23 rejects it as the workflow queue and adopts it as the ingress buffer.

Honesty box · a burst is not a load test

500 workflows against a t4g.micro and ten Fargate tasks is an autoscaling demonstration, not a benchmark. The claim being made is "the scaling signal is the correct one and the control loop closes" — metric published, policy triggered, tasks placed, queue drained, tasks removed. It is not "this handles production traffic," and R3 publishes it in exactly those words. The throughput number that would justify a stronger claim needs a cluster nobody is paying for this month.

And the ingress buffer solves a problem this project does not yet have. With one demo user, nothing is overwhelming the API. It earns its place on two narrower grounds, both worth stating plainly rather than overselling: it gives the system an answer to "what happens to work that arrives while the API is redeploying or RDS is briefly unavailable" — it waits, instead of erroring back at the caller — and it makes the burst below measure the right thing. Firing 500 concurrent HTTP requests mostly exercises Fastify's connection pool; dropping 500 messages on a queue exercises the scaling loop this chunk actually claims.

The ticket demo gains: 500 of it at once, and a graph of the fleet answering.

Gate M12 ✦

Drop 500 messages on the SQS queue; they ingest without a single failed request, and the worker service scales 2 → 10 and back down as the queue drains, both movements visible in the dashboard. An oversized payload round-trips through S3 by reference and a re-fold of the log still equals the projection. And the local seed sweep is still green and still deterministic — this chunk touched the surface, not the core.

→ RESULTS.md: burst size, time to scale out, time to drain, and tasks at peak. "2 → 10" on its own omits whether the control loop closed in a minute or in ten. Also record infrastructure cost per workflow, kept separate from model cost.

Concept · the notification is advisory — exactly like Redis

Postgres NOTIFY is fire-and-forget: if no session is listening when it fires, the message is simply gone. So it can only ever be a hint to re-read, never a source of truth. That is the design doc's existing rule — Redis is advisory; no invariant may ever read from it — applied to a new subject.

Concretely: every SSE payload carries the workflow's step_seq, and a client that reconnects re-reads from the API and catches up from the log. Drop every notification and the page is still correct, just slower. The correctness path does not know SSE exists, the harness never runs the dashboard, and the seed sweep is unaffected — which is exactly what makes this layer safe to add, and cheap to remove under pressure.

One M13 interaction worth writing down: an ALB's default idle timeout is 60 s and will kill an SSE stream that hasn't sent anything. The stream emits a heartbeat comment well inside that window, and the listener's idle timeout is raised. This is the classic way SSE "randomly" dies in production.

Concept · the two measurements that are easiest to lose and matter most

1 · Count the bugs the harness actually caught. "Zero violations across 1,000 seeds" has a hole in it: zero is equally consistent with the code is correct and the harness is weak. The sentence that closes the hole is how many real bugs the sweep surfaced during development — "the sweep caught 6 real correctness bugs, each preserved as a replayable fixture" proves the instrument works, which a clean run never can. The gate-you've-seen-fail rule already manufactures these moments; what is missing is writing each one down the day it happens: what broke, which seed, which invariant caught it.

2 · Always publish the denominator. "Zero duplicate side effects" is weak alone. "Zero duplicates across 14,000 side-effecting operations in 1,000 schedules" is a real claim, because the reader can see the surface area. Zero lost workflows — out of how many started? The denominators cost nothing to record and roughly double the weight of every zero.

Latch · durable execution engine for AI agent workflows
TypeScript · PostgreSQL · AWS (ECS Fargate, RDS, CDK, CloudWatch, S3) · OpenAI + Bedrock · MCP

· Built a durable execution engine for AI agent workflows that resumes killed runs mid-flight with zero duplicate side effects, recording each model decision as an append-only fact instead of replaying it.
· Verified 4 invariants (no duplicate effects, no lost workflows, single owner, budget ceiling) across 1,000+ seeded crash schedules, keeping every failing seed as a permanent regression test in CI.
· Deployed it on AWS with infrastructure as code, autoscaling workers 2 to 10 on queue depth and taking over a killed host's workflow mid-run without re-running its side effects.
· Enforced per-workflow dollar budgets, tool scoping, and risk-gated human approval, adding a second model that reviews every irreversible action before it runs, scored against a 12-case labeled suite in CI.
