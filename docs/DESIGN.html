Latch · Design Doc

A durable execution engine for AI agent workflows — a deployable service plus a TypeScript SDK. Temporal-shaped durability, but the path is chosen by a model at runtime: every model decision is recorded as a durable fact and resumed from, never replayed. Correctness is proven by invariant verification across thousands of seeded fault schedules. Built design-first, one gated chunk at a time.

0. Orientation — the shape before the detail

Two pictures anchor everything below: who Latch talks to, and what one workflow's journey looks like — including the two journeys that matter most, the crash and the human approval. §3 formalises them.

What it is — system context

Latch sits between an application that starts workflows and the model + tools that execute them. The entire correctness story lives inside one box: Postgres is the single transactional source of truth — queue, state, event log, intents, leases, approvals all commit together. Redis exists, but only for advisory concerns (rate limits, backpressure); no invariant ever depends on it.

What it does — one workflow's journey

The straight line down the middle is the happy path. The two branches are the product: a crash mid-step is recovered by lease takeover with no duplicate side effect, and a risky decision suspends the workflow to a human at zero compute. Everything else in this doc exists to make those two branches boring.

Concept · record, don't replay

Classic durable execution (Temporal, Cadence) achieves crash-safety by deterministic replay: re-run the workflow code from the top, feeding back recorded results, and require the code to take the same path every time. Latch inverts this: it records every decision — model outputs, tool outcomes, budget charges — as an append-only fact, and recovery means reading the facts forward and continuing from the last checkpoint. Nothing is ever re-executed to reconstruct state. Two consequences fall out for free: an LLM's non-determinism is irrelevant (the decision is already a fact), and deploying new code mid-run is safe (no replay means no divergence to detect). The price: workflow state must be an explicit, serialisable value, not implicit in code position — §4 makes that concrete.

1. Requirements

Locked project frame (what these requirements assume)

  • Solo, ~1 month at 4–5 h/day — a 120–150 hour budget. Local-first on Docker Compose; free/cheap infrastructure.
  • Node + TypeScript end to end — engine, SDK, API, dashboard, harness.
  • The Temporal test: every feature is checked against "would Temporal already do this?" If durability were the only value, this is a worse Temporal — the agent-native control plane (budgets, loop detection, tool-risk approvals, decision audit) must stay central.
  • Distinct from the other portfolio projects: Replay is AI-reasons/human-acts over telemetry; mint headlines p99/throughput. Latch is AI-acts with durable orchestration, and its headline is correctness under failure and cost control — never latency.
  • Built incrementally as vertical slices — the whole stack grows thin-and-together; the support-ticket demo is the development workload from day one; no capability is "done" until the harness can falsify it.
  • The demo test: a workflow earns an agent only if "could I just write the branches?" is no. (Employee onboarding was rejected on exactly this test.)
Concept · functional vs non-functional

Functional requirement (FR) = what the system does — a feature, a verb ("resume the workflow"). Non-functional requirement (NFR) = how well — here, mostly invariants: properties that must hold on every execution, under every failure schedule. In a correctness-first project the NFRs aren't targets to approach; they're laws the harness tries to falsify.

Functional requirements

MUST The engine + the proof — produces the headline numbers

Non-functional requirements — the invariants & SLOs

Concept · invariant

An invariant is a property that must hold at every observable point of every execution — not on average, not usually: always. I1–I4 below are the four laws of this system. The harness (§9) exists to try to break them across thousands of randomized schedules; one violation is a bug, reproducible from its seed.

Key decisions & trade-offs at this stage

Each lists the real alternatives, the pick, and why it wins. We never just state the choice.

Decision 1 Durability model — replay, record, or plain retries?
Deterministic replay (Temporal's model) — re-run workflow code, feed back recorded results. Battle-tested, and — honestly — it can host an agent loop: put the LLM call in an Activity and its result is recorded, not re-executed. But it demands deterministic orchestration code forever, and its versioning story (patching APIs, worker version sets) makes mid-run deploys genuinely painful.
Plain job queue + retries (BullMQ-style) — simplest, but a retry re-runs the whole handler: side effects double-fire, and there is no step-level resume at all.
Record decisions, resume from facts — every decision and outcome is an append-only fact; recovery reads facts forward from the checkpoint. No replay, no determinism constraint on any code.
We record. Not because Temporal "can't do LLMs" — it can, via activities — but because (a) mid-run deploys become trivially safe, which is a real Temporal pain point worth headlining; (b) the recorded-decision log is exactly the agent-native audit artifact (who decided what, at what cost, with what evidence) that replay histories obscure; and (c) the control plane this project actually exists for — budgets, loop detection, risk-gated approvals — has to be hand-rolled on Temporal anyway. The honest pitch: "Temporal can host an agent; Latch makes the agent the first-class citizen."
Decision 2 Queue — Postgres SKIP LOCKED, or a real broker?
Kafka / RabbitMQ — purpose-built throughput and fan-out. But enqueue and state update now span two systems: the dual-write problem — a crash between "published to broker" and "committed to DB" (either order) leaves a lost or duplicated workflow. Outbox patterns patch this at real complexity cost, and I2's "zero lost workflows" claim would rest on that patch.
Redis streams/lists — fast, but Redis persistence is best-effort by default and it's a second stateful system inside the correctness boundary.
Postgres as the queue — a ready-workflow row is the queue entry; claim with SELECT … FOR UPDATE SKIP LOCKED; enqueue + state transition are one ACID transaction, always.
We pick Postgres. The exactly-once story requires atomicity between queue and state, and one transactional store gives it by construction rather than by pattern. This is an industry-validated approach (Oban, Graphile Worker, River, pg-boss, DBOS all ride it), so it's defensible, not naive. At this project's scale (§2) Postgres has orders of magnitude of headroom; the broker's throughput advantage buys nothing here and costs the invariant.
Decision 3 Side-effect semantics — what may we honestly claim?
"Exactly-once", unqualified — impossible against an external system without its cooperation: the crash window between "call executed" and "outcome recorded" cannot be closed from our side alone. Claiming it unqualified is a claim the first careful reader can demolish.
At-most-once — never retry after an ambiguous failure. No duplicates, but work is silently lost; violates I2's spirit.
Effectively-once — exactly-once intent recording + at-least-once execution + dedupe via a mandatory idempotency key honored at the tool boundary.
We claim effectively-once, precisely. For tools Latch owns (the demo tools), the effects table makes dedupe airtight and the harness verifies it mechanically — that's the headline "zero duplicate side effects, verified at the tool boundary." For external APIs, the key is passed through (Stripe-style) and the guarantee is exactly as good as the provider's idempotency support — stated, not hidden. Structurally, ToolExecutor takes the key as a required parameter: a tool without a key cannot exist, the same philosophy as tool scoping (D7).

2. Capacity & cost estimates

Concept · the headline here is seeds and dollars, not QPS

For a high-traffic service the capacity story is req/s. Latch's story is how many randomized failure schedules the invariants survive and what a workflow costs. Throughput gets sized below strictly so we know the demo won't fall over — it stays out of every headline (mint already owns that axis).

The headline number — invariants over seeds

A full sweep is 5,000 seeds × ~50 events ≈ 250K executed events. With the model and tools mocked deterministically and logical in-process workers (§9), an event costs ~1–2 ms against local Postgres → a full sweep runs in ≈ 5–10 minutes. That makes it a nightly CI job, with a 500-seed slice (< 1 min) as the PR gate. The published claim: zero duplicate side effects, zero lost workflows, zero double-owners, zero budget breaches across 5,000 randomized crash schedules — each number regenerable by anyone from the seeds.

Cost per workflow — and why budgets exist

Support ticket ≈ 6 decisions: 4 routed small (~$0.004) + 2 large (~$0.04) ≈ $0.05/workflow; envelope ceiling $0.50 gives 10× headroom. The dark side: an uncapped loop on a large model burns $0.02+ per iteration, forever — at one stuck workflow per hundred, cost scales with bugs, not load. That asymmetry is why I4 is an invariant with reserve-before-spend enforcement (§7), not a dashboard alert.

Latency & takeover budget — where the time goes

Storage is a non-problem: 1,000 workflows/day × 20 events × 2 KB ≈ 40 MB/day — keep the full audit log forever and never think about retention in v1. Queue pressure at design load is ~0.2 claims/s against a store comfortable at thousands — Postgres-as-queue has ~4 orders of magnitude of headroom (D2 vindicated by arithmetic).

Where this design ends — the scaling tiers

The headroom above is a claim about this load. The honest follow-up is what happens past it, because Postgres-as-queue is not free throughput: every claim is a write and every heartbeat is a write. Knowing the ceiling — and which symptom arrives first — is what makes D2 a decision rather than a preference.

WritePer stepPer ~6-step workflow
Claim — UPDATE lease token + expiry16
Heartbeat — UPDATE expiry every 5 s while running~1–2~9
Checkpoint — INSERT event + projection update, one txn16
Total~4~21–25 write operations

At design load that is ~0.3 writes/s. At one workflow per second — 86,000/day, two orders of magnitude beyond this project — it is ~25 writes/s, still unremarkable.

Concept · what breaks first is vacuum pressure, not throughput

The two tables age very differently. workflow_events is append-only, so it never produces dead tuples — the case Postgres handles best. workflows is updated on every claim and every heartbeat, and each UPDATE leaves a dead tuple behind.

That asymmetry is the whole scaling story. If autovacuum falls behind on the queue table it bloats, index scans slow, claims take longer, workers back up, and the pressure compounds. This shows up long before any throughput ceiling does — which is why the first fixes are storage-level, not architectural.

ScaleWrites/sWhat the design needs
< 10k workflows/day< 3Nothing. This project sits here, ~4 orders of magnitude below the wall.
10k – 1M/day3 – 300Tuning only, no architecture change: aggressive autovacuum on workflows; keep lease_expires_at unindexed so heartbeats stay HOT updates and never touch an index; raise the heartbeat interval 5 s → 15 s, which cuts heartbeat writes 3× at the cost of slower takeover detection (NFR 5 rebalanced, not broken).
1M – 10M/day300 – 2,500Real work: partition workflow_events by month and archive cold partitions to S3; add a connection pooler; and move heartbeats out of Postgres — see below.
> 10M/day2,500+The single-writer ceiling is real. Shard by tenant, one Postgres per shard, routing at the API. This is what Temporal does to its own persistence layer — the pattern is not exotic, it is just work.
Concept · the tier-3 move — split the hot path from the durable path

Heartbeats and events have opposite requirements. A heartbeat is high-frequency and disposable — losing one means an earlier takeover, nothing worse. An event is low-frequency and must be durable forever. Postgres is excellent at the second and merely adequate at the first under churn.

So at tier 3, move heartbeats to Redis and keep the fencing token in Postgres, incremented once per claim rather than once per beat. The churn collapses while the token stays authoritative in the same store as the writes it guards, so D11's fencing argument is untouched.

This does not contradict D4 — it is D4's rejected option becoming correct at a load D4 was not written for. D4 rejected split liveness because two systems would hold an opinion about it for no benefit at this scale. At tier 3 the benefit exists. And the failure mode stays advisory in exactly the sense D4 demands: if Redis dies, every lease looks expired, a wave of takeovers happens, and fencing makes every displaced worker's write match zero rows. Extra work, no corruption.

Honesty box · none of this is measured

The tiers above are arithmetic and published experience from the Postgres-queue implementations named in D2 (Oban, River, Graphile Worker), not benchmarks run against Latch. The only number here this project will actually produce is its own: ~0.3 writes/s, and the sweep timings from M4. Presenting the rest as measured would be the same error the harness exists to prevent.

Key decisions & trade-offs

Decision 4 Where do leases live — Postgres, Redis, or both?
Heartbeats in Redis, leases in Postgres — the original sketch: Redis is "fast" for frequent beats. But now two systems hold an opinion about liveness, and during a partition you must answer which is authoritative — a split-brain question bought for no benefit.
Everything in Redis — fast, but the queue/state txn boundary (D2) is broken again; correctness now depends on Redis persistence.
Leases + heartbeats wholly in Postgres — a heartbeat is UPDATE workflows SET lease_expires_at = now() + ttl WHERE id = $1 AND lease_token = $2. One authority.
We keep liveness entirely in Postgres. A heartbeat every 5 s per active workflow is negligible write load at this scale, and the one-transactional-store narrative — the same argument that rejected Kafka — stays unbroken. Rule, stated in the doc and enforced in review: Redis is advisory; no invariant may ever read from it.
Decision 5 Lease granularity — per step, or held across steps?
Hold the lease across steps — claim once, heartbeat, run many steps. Fewer claim queries, sticky locality; but a takeover waits on TTL from wherever the worker died, and fairness needs explicit yielding.
Pin a worker for the workflow's life — simplest mental model, but a suspended workflow would hold a worker: violates NFR 7 outright.
Claim → one step → checkpoint → release — the lease covers exactly one step; between steps the workflow is just a ready row again.
We lease per step. The claim query costs ~1 ms; the step it wraps costs 1–10 s of model call — the overhead is noise (§2 arithmetic), and in exchange every crash window shrinks to one step, takeover is maximally fresh, fairness is automatic, and suspension falls out naturally (don't re-enqueue until resumed). Hold-across-steps remains a pure optimization behind the same claim interface if ever needed — the design doesn't foreclose it.

Key decisions & trade-offs

Decision 6 What is a workflow definition?
Full code DSL (Temporal-style) — author every branch in code. Maximum control, but the agent is decorative: if you can write the branches, you didn't need a model (the demo test).
Pure goal prompt (AutoGPT-style) — hand the model a goal and every tool. Maximum autonomy, unboundable behavior; impossible to audit or budget honestly.
Phased envelope — a workflow = goal + phases + done-criteria + envelope; each phase is either plain code or an agent step with a scoped tool subset. The step sequence within a phase is emergent; the phase structure is not.
We pick phased. "Deterministic by default, agentic only where judgment is required" is the design position — extraction and dispatch are code (cheap, testable); investigation and policy judgment are agent phases (where a model earns its cost). The envelope makes autonomy boundable; the phase boundary gives the harness natural checkpoints.
Decision 7 Tool guardrails — structural or prompt-based?
Prompt-based — "you may only use these tools." A convention the model can violate under adversarial or confused input; unfalsifiable in review.
Structural scoping — the dispatcher resolves tool calls against the phase's tools array; a name not in the array raises a structured error event, before any intent is written.
Structural, always. A guardrail the model cannot cross by being wrong is categorically different from one it's asked not to cross. Same doctrine as the mandatory idempotency key (D3) and the budget reserve (§7): make the illegal state unrepresentable, not discouraged.
Decision 8 State — mutable row, pure event sourcing, or both?
Mutable state row only — simple reads, but history is gone: no audit, no "why did it decide that," and recovery has nothing to reason from.
Pure event sourcing — events only, fold on every read. Maximal purity; but the queue needs an indexable "ready" flag and dashboards need cheap lists — folding everywhere is gratuitous pain.
Events authoritative + projected row — append-only workflow_events is the truth; the workflows row is a projection (status, step_seq, budget counters) updated in the same transaction as the append.
Both, with a clear master. Same-transaction projection means the row can never drift from the log (a latch verify command re-folds and diffs, as a CI check). The log gives audit + recovery + the harness's witness; the row gives the queue and dashboard O(1) reads. This is textbook CQRS-lite, minus the eventual-consistency pain because it's one store.
Decision 9 What drives approval policy?
Per-workflow ad-hoc rules — each definition hand-codes when to ask a human. Repetitive, and reviewers can't reason about coverage.
Tool-risk classification — every tool declares a risk class (read / write / irreversible); the envelope maps class → rule (auto, approve over $threshold, always approve). The engine enforces the map at the intend stage.
Risk classes drive policy. It's declarative (auditable in one glance), it composes (new tool → declare its class → policy applies), and it's the agent-native feature Temporal has no analog for — promoted from the risk-list to a core mechanism precisely because it passes the Temporal test.

4. Deep dive — event log & state machine

The substrate everything else writes to. Two tables carry the design: an append-only event log (the truth) and a projected workflow row (the queue + the dashboard's read model).

Concept · event sourcing & projections

Event sourcing: persist changes as an ordered log of immutable events; current state is a fold (reduce) over them. A projection is a derived, queryable view of the log. Latch's twist: the projection is updated in the same transaction as the append, so it is never stale — we take event sourcing's audit and recovery superpowers and skip its eventual-consistency tax.

-- The two load-bearing tables (abridged; full DDL in migrations)
CREATE TABLE workflows (
  id              uuid PRIMARY KEY,
  tenant_id       text NOT NULL,
  def_name        text NOT NULL,  def_version int NOT NULL,
  status          text NOT NULL,            -- ready|running|suspended|completed|dead_lettered|cancelled
  phase_idx       int  NOT NULL DEFAULT 0,
  step_seq        int  NOT NULL DEFAULT 0,  -- next event sequence
  state           jsonb NOT NULL,           -- the projected S
  run_after       timestamptz NOT NULL DEFAULT now(),
  lease_owner     text,  lease_token bigint NOT NULL DEFAULT 0,
  lease_expires_at timestamptz,
  budget_reserved_c int NOT NULL DEFAULT 0, budget_spent_c int NOT NULL DEFAULT 0,
  attempts        int NOT NULL DEFAULT 0
);
CREATE INDEX ON workflows (status, run_after);          -- the queue index

CREATE TABLE workflow_events (
  workflow_id uuid NOT NULL REFERENCES workflows(id),
  seq         int  NOT NULL,
  type        text NOT NULL,
  payload     jsonb NOT NULL,
  recorded_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (workflow_id, seq)             -- ← collision point: a stale writer's seq already exists
);

Decision 11 Write-collision defense — advisory locks or the (id, seq) key?
Advisory locks / SELECT FOR UPDATE on the workflow row for the whole step — holds a DB lock across a 10-second model call: connection pinned, vacuum blocked, and a crashed holder stalls everyone until timeout.
Optimistic: PRIMARY KEY (workflow_id, seq) + fencing token predicate — writers never hold locks across I/O; a stale writer's append simply fails its WHERE or violates the PK.
Optimistic, two layers. The fencing predicate (§5) rejects a zombie's write by token; the (id, seq) primary key is the belt-and-braces beneath it — even a pathological interleaving cannot record two events at one sequence. Locks held across model calls are how systems die in demos.

5. Deep dive — queue & leases

How work is claimed, kept, stolen, and — critically — how a stolen-from worker is prevented from doing damage when it wakes back up.

-- CLAIM: one atomic statement — expired leases are just another claimable row
UPDATE workflows w
SET    status='running', lease_owner=$worker, lease_token=lease_token+1,
       lease_expires_at=now()+interval '15 seconds'
WHERE  w.id = (
  SELECT id FROM workflows
  WHERE  (status='ready'  AND run_after <= now())
      OR (status='running' AND lease_expires_at < now())   -- ← takeover path
  ORDER BY run_after
  LIMIT 1
  FOR UPDATE SKIP LOCKED                                    -- contended rows are skipped, not waited on
)
RETURNING w.id, w.lease_token;

-- HEARTBEAT (every 5s while a step runs)
UPDATE workflows SET lease_expires_at=now()+interval '15 seconds'
WHERE id=$wf AND lease_token=$token;    -- 0 rows updated ⇒ we lost the lease: abort the step

-- FENCED APPEND (every write the worker makes)
INSERT INTO workflow_events (workflow_id, seq, type, payload)
SELECT $wf, $seq, $type, $payload
WHERE EXISTS (SELECT 1 FROM workflows WHERE id=$wf AND lease_token=$token);
Concept · fencing token

A lease alone cannot stop a zombie: a worker that pauses (GC, VM stall, network partition), loses its lease to a takeover, then wakes and keeps writing. The fix is a fencing token — a number that increments on every claim; every write carries it and is rejected if it's stale. Latch's lease_token bumps on claim, so the zombie's writes hit a WHERE that matches zero rows. This is the canonical solution (Kleppmann's DDIA lock-service example) — and I3 exists to prove ours actually works.

Decision 12 Recovering expired leases — reaper process or claim-time?
A background reaper — a sweeper resets expired leases to ready. Another process to run, monitor, and crash; a gap between sweep intervals adds takeover latency.
Claim-time recovery — the claim query's OR-branch treats an expired-lease row as claimable directly; takeover is a claim.
Claim-time. One less process, zero added latency (the next hungry worker performs the takeover), and the token bump happens atomically inside the same claim UPDATE — no window where the row is "reset but unclaimed."
Decision 13 Heartbeat 5 s / TTL 15 s — why these numbers?
Tight (1 s / 3 s) — fast takeover, but a routine GC pause or laptop hiccup triggers spurious takeovers; fencing makes that safe but each one wastes a step's model spend.
Loose (30 s / 90 s) — nearly no false takeovers, but NFR 5's <20 s recovery is blown and the kill-demo looks sluggish.
5 s / 15 s — TTL = 3 missed beats — tolerates two straight missed heartbeats before takeover.
3-missed-beats is the classic ratio (same shape as Raft election timeouts ≫ heartbeat interval). Worst honest takeover ≈ TTL + claim ≈ 16 s < the 20 s budget, while a single slow GC doesn't cause churn. Config knobs, defaults defended.

6. Deep dive — the effectively-once tool layer

The invariant I1 lives here. The mechanism is one rule: no side effect without a prior intent, no intent without an idempotency key, no retry without consulting the key.

Decision 14 Idempotency-key derivation — per attempt or per step?
Per attempt (wf·step·attempt) — every retry gets a fresh key ⇒ every retry re-executes ⇒ the dedupe is decorative. This is the classic silent bug in home-rolled idempotency.
Random UUID minted at execute time — worse: the crash loses the key itself, so the retry can't even ask the right question.
Per step (wf_id · step_seq), minted into the intent record — stable across every retry of that step, durable before any effect.
Step-scoped, recorded in the intent. The key must name the logical effect, not the physical attempt — that's the entire point of the key. Writing it into the intent event before execution means even the §5 "dangerous window" retry recovers the key from disk and dedupes correctly.
Decision 15 Who answers "did this key already run?"
Each tool self-implements dedupe — N tools × N hand-rolled checks; one forgetful tool silently breaks I1 for everyone.
Engine-level effects table for owned tools; pass-through for external APIs — the dispatcher inserts into effects in the same transaction as the tool's local effect; external calls carry the key to providers that honor it (Stripe et al.).
Centralize it. For owned tools the unique constraint makes I1 mechanical — the harness can count rows. For external APIs we state the honest boundary (D3): the guarantee equals the provider's idempotency support, and the intent log still bounds the blast radius to "at most once ambiguous call, listed in the audit."
Honesty box · what "effectively-once" does not cover

A third-party API with no idempotency support can, in the §5 dangerous window, receive a duplicate call — no client-side design can prevent that, only document it. Latch's claim is scoped: zero duplicates through the tool layer for key-honoring tools (verified across all seeds), and a complete intent audit for everything else. This is the boundary of the claim, stated rather than discovered.

7. Deep dive — the agent runtime

Where the model meets the envelope. An agent phase is a loop: build context from recorded facts → call the model → record the decision → dispatch tool calls (via §6) → check done-criteria — all inside hard resource walls.

Decision recording — the agent-native audit row

Every model call becomes a decision_recorded event: model id, prompt hash (not the full prompt — size), input/output tokens, dollar cost, latency, and the structured output. Resume reads the fact and never re-asks — the harness asserts model-call counts to prove it. This log is the answer to "why did the agent do that?" — per step, with costs — the artifact a Temporal history can't give you.

Concept · reserve-before-spend

Budget checks after a call can overshoot the ceiling (the call already happened) — and concurrent steps make it worse. So the envelope works like a hold on a credit card: reserve the worst-case cost of the next model call (from the tier's price table) in the claim transaction; if reservation would cross the ceiling, the call never happens; settle the actual cost at record time and release the difference. I4 becomes arithmetic: reserved + spent ≤ ceiling is checked as a WHERE clause, and the harness asserts it on every log.

Decision 16 What happens on a stall trip?
Hard-fail to DLQ — safe and simple, but a stalled workflow often has real partial progress a human could finish in one decision; killing it wastes that.
Auto-summarize and force done — the model grades its own stuck homework; unbounded wrongness risk on exactly the workflows already going wrong.
Suspend to a human with a progress summary — trip ⇒ stall_detected event ⇒ the §8 suspension machinery, with the recorded decisions as the case file.
Suspend to human. It reuses HITL wholesale (no new machinery), converts a failure mode into an escalation-precision data point (Tier 3 metrics), and matches the design position: when judgment runs out, route to a human — don't guess harder.
Decision 17 Model routing — static per-phase tiers or a dynamic classifier?
Dynamic complexity classifier — a small model routes each call. Adaptive, but adds a model call to route a model call, and the routing itself becomes a nondeterministic thing to debug and eval.
Static per-phase tiers (modelTier: 'small' | 'large') — the definition author declares where judgment lives; extraction/triage phases ride the cheap tier.
Static tiers for v1. Predictable, zero overhead, and cleanly measurable: run the quality suite with routing on vs. all-large, publish "X% cost saved, zero quality regression" (Tier 2's metric). A learned router is a pre-registered stretch — it needs the eval suite to exist first anyway.

The critic — verification before irreversible actions

For intents whose tool is risk-class irreversible, a second model role — the critic — reviews the proposer's decision against the phase goal and the prose policy before the intent is written: agree ⇒ proceed to intend; disagree ⇒ suspend to a human with both opinions attached (§8). The critic's review is itself a decision_recorded event (model, tokens, $), so the audit trail shows two independent judgments in front of every irreversible effect. Honest naming: this is a proposer/critic pattern — the minimal, defensible form of multi-agent orchestration — not a swarm, and the doc never claims otherwise.

Decision 18 Guarding irreversible actions — self-check, critic, or swarm?
Self-check ("are you sure?") — re-ask the same model to verify its own conclusion. Nearly free, but a correlated failure: the reasoning that produced the error re-produces it on review.
Full multi-agent pipeline — planner/researcher/executor/reviewer roles on every step. Maximum keyword coverage, but cost and latency multiply everywhere, and most steps carry no irreversible risk — unbounded machinery for a bounded problem.
Proposer/critic on irreversible intents only — an independent model call (fresh context: the decision, its evidence, the policy — no sunk reasoning) gates exactly the actions that cannot be undone; disagreement escalates to a human, never auto-overrides.
Critic, scoped by risk class. It composes with existing machinery (risk classes decide where it runs, D9; HITL absorbs disagreements, §8), it's a structural guardrail in the doc's own doctrine, and it's measurable: the labeled suite scores catch rate and false-block rate (Tier 3). Cost stays bounded because irreversible intents are rare by construction.

8. Deep dive — HITL & the control plane

Suspension, approvals, escalation, cancellation, dead-lettering — the machinery that lets a workflow wait on a human for hours at zero cost, and fail permanently without lying about what it already did.

Suspension mechanics — sleeping in rows

At the intend stage, the envelope's policy map (risk class → rule, D9) may demand approval. Then: an approvals row is written (with due_at for escalation), a suspended event appended, status flips to suspended, and the lease is released. Nothing holds a process, a connection, or a lease — the workflow is pure data (NFR 7). Approval via API/dashboard appends approved, flips status to ready, and the next hungry worker picks it up — resume is just a claim. Escalation needs no scheduler process: the claim query's family includes due_at <= now() approval rows checked by the API's poll — a timer is a row with an index, the same trick as the queue itself.

Decision 19 Escalation — reminder, reassignment, or auto-decide?
Nag the same approver — reminders decay instantly; the workflow can starve forever on one absent human.
Auto-approve/deny on timeout — an unattended machine making the exact decision policy said needs a human — self-contradiction.
Escalate to a backup approver chain — due_at passes ⇒ escalated event, approval reassigned to the next approver in the envelope's chain, new due_at.
Escalate along a chain. Deterministic, auditable (escalated events are Tier 3 escalation-precision data), and it terminates: the chain's end is a policy choice (final timeout ⇒ deny + DLQ), stated in the envelope rather than improvised.

Retries, the error taxonomy, and the dead-letter queue

Concept · error taxonomy & dead-lettering

Retry policy must branch on error class, not error presence. Transient (timeouts, 429s, 5xx): retry with exponential backoff + jitter, capped attempts. Permanent (validation failure, 4xx, tool rejects args): retrying is self-harm — zero retries. Ambiguous (crash in the dangerous window): retry through the dedupe layer (§6). Exhausted or permanent ⇒ dead-letter: stop consuming resources, preserve everything, surface to a human.

The DLQ row carries the committed-side-effects list — extracted mechanically from the intent/outcome events: what already happened (refund issued, email sent) that a human may need to compensate. No automated saga compensation in v1 (WON'T, D3 honesty applies) — but the operator never has to archaeology the answer to "what did it already do?"; the row states it. Manual requeue (reset attempts, back to ready) is the recovery path. Cancellation reuses the same shape: observed at the next step boundary (leases are short, so that's soon), and the cancel record carries the same committed-effects extract.

Decision 20 Retry ceilings — how many, and where declared?
Retry forever with backoff — "eventually it'll work" — except permanent failures never do; the queue silts up with undead work and the failure is invisible precisely because it never terminates.
Per-class caps in the envelope (default: transient ×5 with jittered backoff, permanent ×0), then DLQ
Cap and dead-letter. Bounded badness beats optimistic infinity in an audited system: the DLQ converts silent churn into a visible, actionable queue with provenance. Defaults in the envelope so a definition can tighten them per risk profile.

9. Deep dive — the verification harness the metric

Everything so far claims correctness; this section is what makes the claims numbers. The harness is a seeded schedule generator, a deterministic runtime substitution, and an invariant sweep over the one witness that never lies: the event log.

Concept · property-based verification vs chaos testing

Chaos testing perturbs a live system and watches dashboards — great for finding surprises, weak for proofs (unreproducible). Property-based verification declares invariants, generates randomized executions from a seed, and asserts the invariants after every run — the FoundationDB simulation / Jepsen lineage. The seed is the superpower: any failing run is reproduced exactly by its seed and becomes a permanent regression fixture. (Replay uses fault injection to generate demo incidents; Latch uses seeded schedules to falsify invariants — different instrument, deliberately.)

// Invariants are pure functions over the finished log — no privileged engine access
I1: for every idempotency key: executions(log, key) === 1        // intents may retry; effects may not
I2: every workflow_started reaches completed | dead_lettered | cancelled | suspended (no orphans)
I3: fenced-write violations === 0  AND  no two overlapping lease intervals per workflow
I4: at every prefix of the log: reserved + spent ≤ envelope.budgetUsd

What makes a seed reproducible — and what doesn't

Three substitutions make a schedule deterministic: logical workers (concurrent tasks in one process, not OS processes — the scheduler interleaves them by seed), a fake ModelClient (seeded, deterministic outputs — also: 5,000 seeds would be absurd against a real API), and an injected clock (lease expiry and due_at are driven by the schedule, not wall time). Crash points are named checkpoints at every §5/§6 boundary (after_claim, after_decision, after_intent, after_execute, after_settle…); the seed chooses among them. A schedule is a replayable list of (step, crash-point, fault) choices — which is exactly why a failing seed replays exactly.

Honesty box · the reproducibility boundary

Seeded schedules reproduce failures caused by injected faults at named points. They do not control OS scheduling or hardware races — a failure depending on a torn interleaving between checkpoints won't replay. Closing that gap is full deterministic simulation (virtualized I/O and time) — pre-registered as the stretch goal, not claimed in v1. Additionally, one real kill -9 demo (OS processes, real crash) runs beside the logical harness — the harness proves the invariants; the kill-demo proves the harness isn't a toy.

The gate-you've-seen-fail rule

A green invariant that has never been red is trusted on faith. Discipline, applied at each chunk: after wiring an invariant, deliberately break the mechanism it guards (comment out the fencing predicate; derive keys per-attempt), watch the sweep go red on a specific seed, then revert. Only then is green evidence.
